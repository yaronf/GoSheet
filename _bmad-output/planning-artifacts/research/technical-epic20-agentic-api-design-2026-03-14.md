# Epic 20: Agentic API Access Layer — Technical Design
_2026-03-14_

---

## 1. Goals

AI agents (and power users via scripts) can read spreadsheet data and apply changes through a structured, safe API. The user can discard everything an agent did in one operation. No human approval step is required per-change — the agent operates autonomously and the user's safety valve is session rollback.

Design is intentionally forward-compatible with a remote (multi-user) deployment, but v1 is local-only (Electron + Go child process on localhost).

---

## 2. Threat Model

The Go server is a child process bound to an ephemeral localhost port — not internet-exposed. The agent is a trusted tool running on the same machine (e.g., Claude Code, a script). The relevant risks are:

- **Port scanning:** any local process can discover and call the API. Mitigated by bearer token auth on all endpoints (including existing ones — this is a retroactive security improvement).
- **Agent mistakes:** authorized agent writes bad data, inserts too many rows, etc. Mitigated by session rollback.
- **No formula injection restriction, no per-token size limits** — the agent is trusted, guardrails are operational (rollback) not preventive. Agents are explicitly blocked from file management operations (`/api/file/*`) regardless of scope, to keep them within the data layer.

No auth tokens needed beyond the bootstrap token + scoped agent token. No JWT, no signed tokens — opaque random tokens mapped to scope structs in server memory are sufficient for v1. If the app goes remote, this layer is where you'd introduce signed tokens and proper user identity.

---

## 3. Token Model

### 3.1 Bootstrap Token

Generated by the Go server at startup using a CSPRNG (32 bytes, base64url encoded). Passed to Electron on fd 3 alongside the port:

```
PORT=49213
TOKEN=<bootstrap-token>
```

Electron stores both, injects the token into the renderer. **All existing API calls gain `Authorization: Bearer <bootstrap-token>` from this point forward.** This retroactively secures the existing API against local port scanners.

### 3.2 Agent Token

Issued by the server in exchange for the bootstrap token:

```
POST /api/agent/token
Authorization: Bearer <bootstrap-token>
Body: { "scope": "rw" }
```

Scope options:
- `"ro"` — read-only (GET agent endpoints only)
- `"rw"` — read + write (all agent endpoints)

Returns: `{ "agentToken": "...", "agentId": "..." }`

The server takes a **history marker** at this point (records the current top of the user's undo stack, so rollback knows where to stop).

**One active agent session per file at a time.** A second `POST /api/agent/token` for the same file returns 409 while a session is active.

---

## 4. Bootstrap URL

The single artifact handed to the agent:

```
http://localhost:<port>/api/agent/bootstrap?token=<agent-token>
```

The UI constructs this from the ephemeral port (already known to Electron) and the agent token returned from §3.2. Displayed in a modal with a copy button.

The agent GETs this URL and receives everything needed to start working:
- Validated token confirmation
- Tool definitions (see §11)
- Workbook summary (file path, sheet name, dimensions)
- Base URL for all subsequent calls

One GET, fully bootstrapped.

---

## 5. Agent Session Lifecycle

```
FE: POST /api/agent/token          → agentToken, agentId (server marks history)
FE: display bootstrap URL to user
User: copies URL, pastes into agent tool

Agent: GET  /api/agent/bootstrap   → tool defs + workbook context
Agent: GET  /api/agent/range       → read data
Agent: POST /api/agent/patch       → apply changes (attributed to agentId)
Agent: POST /api/agent/commit      → checkpoint: history flushed, token stays alive
Agent: GET  /api/agent/range       → read more, do more work...
Agent: POST /api/agent/patch       → apply more changes
Agent: POST /api/agent/end         → declare success, token revoked

  — OR (user-initiated end) —

User: clicks "Discard Session"
FE:   POST /api/agent/rollback     → history unwound to marker, token revoked

  — OR (user-initiated clean close) —

User: clicks "End Session"
FE:   POST /api/agent/end          → token revoked, changes already committed remain
```

---

## 6. Undo Architecture

Agent operations use the **existing command infrastructure** (`History`, `Command` interface with `Do()`/`Undo()`). A **separate `History` instance** is maintained per agent session, independent of the user's history.

- `Cmd+Z` in the UI only touches the **user's** history — agent changes are invisible to it
- **Commit** (`POST /api/agent/commit`) collapses all agent history since the last commit into a single `AgentCommitCommand` and transfers it into the **user's** undo history. The user can undo the entire committed block with one `Cmd+Z` (description: e.g., "Agent: 3 patches, 47 cells changed"). Token remains active; a new history marker is set.
- **End session** (`POST /api/agent/end`) revokes the token. Any uncommitted agent history since the last commit is collapsed and transferred to the user's undo history the same way.
- **Rollback** (`POST /api/agent/rollback`) drains the agent history back to the session-open marker (or the last commit marker, whichever is more recent) by replaying `Undo()` calls in reverse order, then revokes the token.
- **If the user edits a cell that the agent has also written, and the session is then rolled back, the user's edit to that cell is overwritten.** This is an accepted tradeoff for a local single-user app. The active session indicator makes this risk visible.

No new snapshot mechanism is needed. The existing per-command before/after snapshots in the command pattern are sufficient.

## 7. API Surface

All agent endpoints require `Authorization: Bearer <agent-token>`. Scope is enforced per-endpoint server-side. Agent tokens are rejected on any `/api/file/*` endpoint regardless of scope.

### Session management (bootstrap token required)
```
POST /api/agent/token         # issue scoped agent token
```

### Session management (agent token required)
```
GET  /api/agent/bootstrap     # entry point: tool defs + workbook context
POST /api/agent/commit        # checkpoint: flush agent history, keep token alive
POST /api/agent/end           # close session cleanly, revoke token
POST /api/agent/rollback      # unwind agent history to last commit/open, revoke token
```

### Data access (ro or rw scope)
```
GET  /api/agent/workbook      # sheet summary: file path, dimensions
GET  /api/agent/range         # read cells by A1 notation (?range=A1:D20)
```

### Mutations (rw scope only)
```
POST /api/agent/patch         # batch operations (see §8)
```

Existing `/api/*` endpoints are unchanged and continue to work with the bootstrap token (used by the renderer). Agent tokens are scoped to the `/api/agent/*` namespace only.

## 8. Patch Format

A patch is a batch of operations applied atomically through the command pattern. Each op maps to an existing command type.

```json
{
  "description": "Fill column B with revenue formulas",
  "ops": [
    { "op": "SetCell",    "row": 0, "col": 1, "value": "=A1*1.2" },
    { "op": "SetCell",    "row": 1, "col": 1, "value": "=A2*1.2" },
    { "op": "ClearRange", "startRow": 5, "startCol": 0, "endRow": 10, "endCol": 3 },
    { "op": "InsertRow",  "row": 3 },
    { "op": "DeleteRow",  "row": 7 },
    { "op": "SetStyle",   "row": 0, "col": 0, "styleId": 1, "alignment": "center" },
    { "op": "AddStyle",   "name": "Highlight", "fontColor": "#FF0000", "fillColor": "#FFFF00" },
    { "op": "ClearFormat","startRow": 2, "startCol": 0, "endRow": 4, "endCol": 3 }
  ]
}
```

`SetStyle` accepts a `styleId` (reference to a named style) plus an optional `alignment` override. The agent works with named styles rather than raw font/fill/border properties; new named styles are created via `AddStyle` if needed. The `description` field is recorded in the audit log only — it does not surface in the user's undo stack. Server applies ops in order; if any op fails validation, the entire patch is rejected (no partial apply). All ops in an accepted patch are recorded as a single entry in the agent's history.

After a successful patch, the spreadsheet is marked as having unsaved changes — the user saves explicitly as normal.

---

## 9. Audit Log

Append-only JSON file in Electron's `userData` directory (`~/Library/Application Support/GoSheet/agent-audit.jsonl`). Per-app, survives file switches.

Each line is a JSON record:

```json
{
  "ts": "2026-03-14T14:23:01Z",
  "agentId": "agt_abc123",
  "event": "patch",
  "filePath": "/Users/alice/budget.sheet",
  "description": "Fill column B with revenue formulas",
  "opsCount": 6,
  "outcome": "applied"
}
```

Events: `session_open`, `patch`, `commit`, `end`, `rollback`.

## 10. UI

**Token issuance:**
- Toolbar button (key icon) + menu item (File → "Create Agent Session...")
- Opens modal showing:
  - Bootstrap URL (`http://localhost:PORT/api/agent/bootstrap?token=...`)
  - Copy button
  - Scope selector (R/O vs R/W)
  - Brief instruction: "Paste this URL into your AI tool to grant it access to this spreadsheet"

**Active session indicator:**
- Status bar shows "Agent session active" while a session is open
- Two buttons visible while session is active:
  - "End Session" — calls `POST /api/agent/end`, changes remain, token revoked
  - "Discard Session" — calls `POST /api/agent/rollback`, changes since last commit unwound, token revoked
- Session indicator clears when agent calls `end` autonomously

**Unsaved changes:** Agent patches mark the spreadsheet as modified. The file status indicator ("Unsaved") works as normal — the user saves explicitly.

## 11. Skill / Agent Bootstrapping

`GET /api/agent/bootstrap` returns a JSON response containing:

1. **Tool definitions** — formal tool use JSON for each agent endpoint (`get_workbook`, `read_range`, `apply_patch`, `commit`, `end`, `rollback`). Formatted using the OpenAI function calling schema (JSON Schema-based `input_schema`), which is accepted by all major LLM providers (Anthropic, OpenAI, and most open-weight models) and is the closest existing cross-vendor standard. An agent receiving this can immediately begin tool-calling without any hardcoded knowledge of the API.
2. **Workbook context** — current file path, sheet dimensions, a summary of non-empty regions.
3. **Session metadata** — agentId, scope, base URL.

A human-readable version (Markdown) will be maintained in the docs for users who want to paste context into Claude.ai or similar tools manually.

---

## 12. Forward Compatibility Notes

This design is intentionally structured for future remote deployment:

- Bearer token auth is already in place; replacing opaque tokens with signed JWTs requires only server-side changes
- Scope model (`ro`/`rw`) maps cleanly to a future RBAC system
- Audit log format is suitable for shipping to a remote logging service
- Single-agent-per-file constraint becomes a distributed lock in a remote deployment
- The bootstrap URL pattern works identically for remote (`https://app.gosheet.io/api/agent/bootstrap?token=...`)
