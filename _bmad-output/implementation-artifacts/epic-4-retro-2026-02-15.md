## Key Insights

### 1. "Done" Means Tested and Working
> All the checklists, story documents, and commit messages in the world don't matter if the feature doesn't work when the user tries it. Epic 4 taught us that "done" means "tested and working", not "code exists and compiles".

**Evidence:**
- 8/8 stories marked "done" with checklists complete
- 0/8 stories actually worked without fixes
- All issues found in first manual test session

**Lesson:** Manual testing is mandatory for UI features that can't be unit tested.

### 2. Web Mode Tests Don't Validate Native Mode
> The Playwright tests run against the web mode HTTP server. They don't test native file dialogs, Wails IPC communication, keyboard shortcuts, or macOS integration.

**Evidence:**
- 42 Go unit tests + 32 Playwright tests all passing
- Native app completely broken (Load/Save buttons didn't work)
- Different code paths: web mode uses HTTP fetch, native mode uses Wails IPC

**Lesson:** Need dedicated native testing infrastructure for native-specific features.

### 3. Manual Testing is a Bottleneck
> Without automated native testing, every native feature requires manual testing, creating a bottleneck and risk of shipping broken code.

**Evidence:**
- Epic 4 required manual testing to discover all issues
- Future epics (CSV, macOS Integration, Welcome Screen) will have same problem
- Manual testing doesn't scale and isn't repeatable

**Lesson:** Invest in automated native testing infrastructure to eliminate bottleneck.

## Significant Discovery: Testing Gap Requires Epic Plan Change

### Discovery
Epic 4 revealed that **web mode tests provide zero coverage for native features**. Without automated native testing, we're shipping blind and will repeat Epic 4's "ship broken code" pattern.

### Impact on Roadmap
Current Epic 5 (CSV Import/Export) assumes we can continue building features, but Epic 4 showed we can't safely build more native features without testing infrastructure.

### Solution Found
**Technical research completed** (Feb 15, 2026): `_bmad-output/planning-artifacts/research/technical-macos-native-testing-wails-research-2026-02-15.md`

**Key Findings:**
- **Recommended tool:** pyax (January 2026, Mozilla-backed Python accessibility library)
- **Architecture:** Hybrid testing (70% Go unit, 20% web integration, 10% native smoke)
- **Implementation:** 5 stories, 4-6 weeks, incremental adoption
- **Coverage:** 5-10 native smoke tests for critical paths
- **ROI:** $2,500-4,000 investment, ~2-year payback period

### Decision: Insert Epic 5 (Native Testing Infrastructure)

**Required Changes:**
1. ✅ Insert new Epic 5: Native Testing Infrastructure (5 stories)
2. ✅ Shift existing epics: CSV (5→6), macOS Integration (6→7), Welcome Screen (7→8)
3. ✅ Update architecture document with hybrid testing strategy
4. ✅ All future native features will have automated test coverage

**Rationale:**
- Eliminates manual testing bottleneck
- Prevents repeating Epic 4's "ship broken code" pattern
- Enables confident iteration on native features
- Investment pays for itself in ~2 years through bug prevention and time savings

**Team Consensus:** Unanimous support for inserting Epic 5 before continuing feature development.

## Proposed Epic 5: Native Testing Infrastructure

**Epic Goal:** Automate testing of native macOS features to eliminate manual testing loop

**Based on:** Technical Research (Feb 15, 2026)

**Stories (5):**

**Story 5.1: Set Up pyax Testing Infrastructure**
- Install pyax and pytest
- Enable macOS accessibility permissions
- Create basic pytest fixtures for app launch
- Verify setup with simple test (app launches)

**Story 5.2: Implement Page Object Pattern**
- Create `GoSheetApp` domain class
- Implement element discovery helpers (find_button, wait_for_dialog)
- Add retry logic and explicit waits
- Document page object usage

**Story 5.3: Create File Dialog Smoke Tests**
- Test: Load button opens file dialog
- Test: Save button opens save dialog
- Test: File dialog filters .sheet files
- Test: Cancel dialog returns gracefully

**Story 5.4: Create Keyboard Shortcut Tests**
- Test: Cmd+O opens file dialog
- Test: Cmd+S saves file (or shows dialog if new)
- Test: Cmd+N creates new spreadsheet

**Story 5.5: Integrate Native Tests into Development Workflow**
- Add native test run instructions to README
- Create `make test-native` command
- Document when to run native vs web tests
- (Optional) Evaluate self-hosted macOS runner for CI/CD

**Success Criteria:**
- All native file operations have automated test coverage
- Tests pass consistently (< 5% flakiness)
- Developers can run tests locally before committing
- Manual testing no longer required for file dialogs
